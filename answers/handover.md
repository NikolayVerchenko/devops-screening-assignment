# Передача инцидента

Влияние: после релиза a81f9c2 API перезапускался с кодом 137, доля ошибок выросла примерно до 12%, p95 до 2.8 с, пользователи получали 502.

Причина: WEB_CONCURRENCY изменили с 2 на 16 на VM с 2 vCPU и 4 GiB без swap. Ядро убило процесс Node по OOM.

Смягчение: выкатить предыдущий образ API или текущий с WEB_CONCURRENCY=2 командой docker compose up -d --no-deps api. PostgreSQL и том db-data не останавливать и не удалять.

Изменение: в production Compose зафиксированы образы, убраны секреты и лишние порты, заданы лимиты памяти и CPU, для ОС остаётся около 1242 MiB, включена ротация логов и ожидание healthcheck. CI запускает проверки до сборки и деплоя, помечает образ API коротким SHA коммита, не печатает SSH-ключ, не выполняет compose down -v, после деплоя проверяет /health и содержит ручной rollback.

Подтверждение: docker compose ps показывает api healthy, curl -fsS http://127.0.0.1/health завершается успешно, в journalctl -k нет нового OOM, доля ошибок и p95 возвращаются примерно к 0.2% и 220 мс.

Оставшийся риск: корневой диск заполнен на 92%, логи контейнеров занимают около 11 ГБ.

Дальше: после стабилизации API освободить место в /var/lib/docker/containers и держать ROLLBACK_TAG равным SHA последнего рабочего релиза.
