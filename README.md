# DevOps pre-screen: production incident

Это практическое задание для кандидата на позицию DevOps Engineer.

## Правила

- Мы оцениваем диагностику, управление риском, проверку результата и ясность handover, а не объём текста или количество найденных замечаний.
- Не используйте реальные cloud-аккаунты, credentials или production-системы.
- Система и registry в задании вымышлены. Исходный код приложения и доступ к VM намеренно не предоставлены: описывайте команды, ожидаемые сигналы и критерии восстановления, но не утверждайте, что фактически выполняли их.

## Задача

Ознакомьтесь с [INCIDENT.md](INCIDENT.md), текущими [docker-compose.prod.yml](docker-compose.prod.yml), [nginx.conf](nginx.conf) и [.gitlab-ci.yml](.gitlab-ci.yml).

Представьте, что вы приняли production-инцидент после автоматического релиза. Нужно:

1. Снизить пользовательский impact.
2. Отделить подтверждённую причину от вторичных рисков.
3. Предложить безопасный rollback.
4. Исправить Compose и CI/CD конфигурацию минимально необходимым образом.
5. Оставить проверяемый handover следующему инженеру.

Полнота не является целью. Хорошо приоритизированное частичное решение лучше большого количества несвязанных изменений.

## Что изменить

### `answers/incident.md`

Укажите:

- первые пять команд, которые вы выполните;
- для каждой команды — какую гипотезу она подтверждает или опровергает;
- подтверждённую основную причину инцидента;
- вторичные риски, уже видимые в evidence;
- первое действие для уменьшения impact;
- rollback plan;
- не более восьми проблем, разделённых на `P0`, `P1`, `P2`.

Формулировки вида «проверю логи» без команды и ожидаемого сигнала не засчитываются.

### `docker-compose.prod.yml`

Подготовьте исправленную версию. Она должна:

- сохранять данные PostgreSQL;
- не содержать secrets в открытом виде;
- использовать immutable или явно заданные версии image;
- не предоставлять лишний внешний доступ;
- не использовать `privileged`, если он не нужен;
- содержать осмысленные health checks;
- ограничивать ресурсы;
- настраивать ротацию container logs;
- оставлять ОС минимум `500 MiB` RAM;
- быть согласованной с вашим incident response.

Memory budget и его краткое обоснование добавьте комментариями в файл или в `answers/incident.md`.

### `.gitlab-ci.yml`

Pipeline должен:

- выполнять тесты до публикации и deployment;
- создавать immutable image tag;
- не выводить secret в лог;
- развёртывать конкретную версию image;
- не удалять database volume;
- проверять состояние сервиса после deployment;
- иметь понятный rollback на предыдущую версию.

Допускаются placeholders для адреса registry, SSH host, защищённых CI variables и отсутствующих app-specific test/build commands. Pipeline должен оставаться внутренне согласованным.

### `answers/handover.md`

Не более 200 слов:

- impact;
- причина;
- mitigation;
- внесённое изменение;
- evidence успешного восстановления или точный критерий и команду, которыми вы подтвердили бы его;
- оставшиеся риски;
- следующее действие команды.



### `answers/AI_USAGE.md`

Не более десяти строк:

- какой AI-инструмент использовался;
- для каких частей;
- какой результат AI вы дополнительно проверяли;
- хотя бы одно предложение AI, которое вы отклонили или изменили;
- почему.

Если AI не использовался, напишите это прямо.

## Локальная проверка

Проверить структуру исходного задания:

```bash
make structure
```

После внесения решения:

```bash
make validate
```

Validator проверяет только структуру, заполняемость, лимиты ответа и базовый синтаксис Compose. Содержательная оценка выполняется отдельно; успешная локальная проверка не означает автоматического прохождения задания.

## Формат отправки

Пришлите HR:

- ссылку на приватный репозиторий; или
- архив репозитория без `.git`, `.env`, credentials и других локальных данных.

Желательно сохранить осмысленную Git history, показывающую последовательность работы.
